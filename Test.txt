sql-- See all tasks that ran in a specific DAG execution
SELECT NAME, STATE, SCHEDULED_TIME, COMPLETED_TIME, ERROR_MESSAGE
FROM TABLE(INFORMATION_SCHEMA.TASK_HISTORY(
    ROOT_TASK_ID => '<root_task_id>',
    SCHEDULED_TIME_RANGE_START => DATEADD('day', -1, CURRENT_TIMESTAMP())
))
WHERE GRAPH_RUN_GROUP_ID = '<specific_group_id>'
ORDER BY SCHEDULED_TIME;
sql-- Compare durations across different DAG runs
SELECT GRAPH_RUN_GROUP_ID,
       MIN(SCHEDULED_TIME) AS dag_start,
       MAX(COMPLETED_TIME) AS dag_end,
       DATEDIFF('minute', dag_start, dag_end) AS total_duration_min,
       COUNT(*) AS tasks_executed,
       SUM(CASE WHEN STATE = 'FAILED' THEN 1 ELSE 0 END) AS failures
FROM TABLE(INFORMATION_SCHEMA.TASK_HISTORY(
    ROOT_TASK_ID => '<root_task_id>',
    SCHEDULED_TIME_RANGE_START => DATEADD('day', -7, CURRENT_TIMESTAMP())
))
GROUP BY GRAPH_RUN_GROUP_ID
ORDER BY dag_start DESC;
In short: Think of GRAPH_RUN_GROUP_ID as a correlation ID for a single DAG execution — it ties together every task that participated in that particular run, making it easy to debug failures, measure end-to-end performance, and audit complete DAG executions.

Step 2: If STATE = SKIPPED (most likely cause)
This means the task has a WHEN condition and it wasn't met:
sql-- Check what the WHEN condition is
SHOW TASKS LIKE 'MY_ROOT_TASK' IN SCHEMA my_db.my_schema;

-- Look at the "condition" column in the output
-- Common example: SYSTEM$STREAM_HAS_DATA('my_stream')
Then verify the stream had no data at that time:
sql-- Check if the stream currently has data
SELECT SYSTEM$STREAM_HAS_DATA('my_stream');

-- Check stream metadata
SHOW STREAMS LIKE 'my_stream' IN SCHEMA my_db.my_schema;
Step 3: Check what happened to child tasks
sql-- Use the GRAPH_RUN_GROUP_ID from Step 1
SELECT NAME, STATE, SCHEDULED_TIME, COMPLETED_TIME,
       DATEDIFF('second', SCHEDULED_TIME, COMPLETED_TIME) AS duration_secs,
       ERROR_CODE, ERROR_MESSAGE
FROM TABLE(INFORMATION_SCHEMA.TASK_HISTORY(
    ROOT_TASK_ID => '<root_task_id>',
    SCHEDULED_TIME_RANGE_START => '2026-03-15'::TIMESTAMP_LTZ,
    SCHEDULED_TIME_RANGE_END   => '2026-03-16'::TIMESTAMP_LTZ
))
WHERE GRAPH_RUN_GROUP_ID = '<group_id_from_step1>'
ORDER BY SCHEDULED_TIME;
The child task behavior depends on the root task state:

Root was SKIPPED → Child tasks never execute at all. They won't even appear in TASK_HISTORY for that GRAPH_RUN_GROUP_ID.
Root FAILED → Child tasks also won't run (unless you've configured ALLOW_OVERLAPPING_EXECUTION or error handling).
Root SUCCEEDED quickly → Child tasks will run, but they may also finish fast if there's no data to process.

Step 4: Inspect the actual query that ran
If the root task did execute (SUCCEEDED or FAILED), use the QUERY_ID to see exactly what happened:
sql-- Check the query profile
SELECT *
FROM TABLE(INFORMATION_SCHEMA.QUERY_HISTORY())
WHERE QUERY_ID = '<query_id_from_step1>';

-- Or for deeper analysis
SELECT *
FROM TABLE(INFORMATION_SCHEMA.QUERY_HISTORY_BY_SESSION())
WHERE QUERY_ID = '<query_id_from_step1>';
Step 5: Compare with a normal run
sql-- Side-by-side: normal runs vs the short run
SELECT GRAPH_RUN_GROUP_ID,
       MIN(SCHEDULED_TIME) AS dag_start,
       MAX(COMPLETED_TIME) AS dag_end,
       DATEDIFF('minute', MIN(SCHEDULED_TIME), MAX(COMPLETED_TIME)) AS total_min,
       COUNT(*) AS tasks_ran,
       LISTAGG(DISTINCT STATE, ', ') AS states_seen
FROM TABLE(INFORMATION_SCHEMA.TASK_HISTORY(
    ROOT_TASK_ID => '<root_task_id>',
    SCHEDULED_TIME_RANGE_START => DATEADD('day', -7, CURRENT_TIMESTAMP())
))
GROUP BY GRAPH_RUN_GROUP_ID
ORDER BY dag_start DESC;
If you see one row with total_min = 0 and tasks_ran = 1 while others show total_min = 15 and tasks_ran = 5+, that confirms the root was skipped or failed before children could fire.
Bottom line: The most common reason for a root task finishing in seconds is a WHEN condition (typically SYSTEM$STREAM_HAS_DATA) returning false, meaning there was no new data to process. When this happens, the entire DAG is skipped — no child tasks run at all. Opus 4.6Extended
